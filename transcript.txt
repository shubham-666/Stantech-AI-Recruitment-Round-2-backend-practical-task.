2. Initial findings
Highest priority - stock reservation / concurrency:
The README says reservations can be retried after timeouts, many can arrive
concurrently, and the system has already oversold. Current stock adjustment does
read -> calculate -> write -> commit, which is vulnerable to concurrent updates.
Reservation must answer two separate questions:
  (1) Atomicity: can two concurrent requests consume the same stock?
  (2) Idempotency: what happens when the agent sends the same reservation twice
      because the first response timed out?

High priority - tenant isolation:
GET /orders/{order_id} filters by Order.id but NOT Order.tenant_id, so it can
look up another tenant's order if the id is known. This class of issue must be
checked across every resource relationship.

High priority - slow order list:
GET /orders loads orders then serializes, accessing customer, every line, and the
product for every line with default (lazy) loading -> likely N+1. The README's
customer complaint makes this non-theoretical. Verify actual query behavior
before choosing eager loading / join / pagination / indexes.

High priority - missing DB constraints:
No uniqueness constraint on StockLevel (tenant_id, warehouse_id, product_id).
Duplicate stock rows could make a reservation update the wrong row.

3. Other areas to inspect
- POST /stock/adjust modifies the same quantity_available reservation will touch;
  an unsafe concurrent adjust could undermine the invariant.
- Order.status is a plain string with no state-transition rules; must decide what
  happens if already reserved / cancelled / completed / partial / retried.
- Transaction boundaries: failure halfway must not leave some lines reserved and
  others untouched; prefer one atomic business operation.
- SQLite concurrency: design for SQLite, not PostgreSQL. Solution must be safe
  against overselling, compatible with SQLite, simple, and explainable. Avoid
  Redis / distributed locks / Celery / Kafka unless actually required.

4. Prioritized review plan
P0 - Reservation correctness: define "reserve", how stock is decremented, what
     happens if a line can't be fulfilled, prevent overselling under concurrency,
     make retries idempotent.
P0 - Tenant isolation: audit every lookup for resource ID + tenant_id; check
     order->customer, order->product, stock->warehouse, stock->product for leaks.
P1 - Order-list performance: verify real query count for GET /orders, then fix
     the demonstrated bottleneck (eager loading / pagination / indexes).
P1 - Database invariants: unique stock level, valid quantities, useful indexes.
P1 - Interaction between /stock/adjust and /reserve: both paths must preserve the
     same invariant.
P2 - API/error semantics: status codes, validation, already-reserved and
     insufficient-stock responses, consistency.
P2 - General production review: session/transaction handling, relationship
     loading, serialization, config, seeding, maintainability.

5. What I deliberately haven't done
Have NOT modified app.py, added indexes, changed the schema, or implemented

answer the real question (atomic + safe under concurrency + harmless retry) from
the actual model rather than dropping in a generic locking pattern. Review/design
